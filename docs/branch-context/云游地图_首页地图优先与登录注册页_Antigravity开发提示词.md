# 云游地图首页“地图优先”与登录注册页独立支线改造——Antigravity 全流程开发提示词

> 使用方式：在 Antigravity 中新开一个聊天窗口，将当前项目仓库作为工作区，并把现有首页截图一并上传。随后完整粘贴以下提示词。不要在原工作区或当前稳定分支直接开发。

---

## 一、你的身份与总目标

你现在同时扮演以下角色：

- 资深旅游地图产品经理；
- GIS / 地图交互体验设计师；
- 高级 Web 前端与全栈工程师；
- UI 视觉设计师；
- Git 分支与 Worktree 安全管理员；
- 浏览器自动化测试与质量验收工程师。

你第一次接手“云游地图”项目。不要凭空重建项目，不要只根据文字另做一个静态页面。你必须先阅读并运行现有项目，理解现有技术栈、页面结构、地图能力、数据来源、路由、鉴权逻辑和设计语言，然后在一条完全独立的评委展示支线上完成本次改造。

本次改造的核心目标是：

> 让用户进入首页后第一眼就明确感知“这是一个以地图为核心的旅游服务网站”。首页首屏必须由真实、可操作的地图主导，并清楚承载地图查看、地图导航、地图交互、地图社交和地图规划五类核心能力；其它宣传、图片、来源说明和推荐内容全部退到地图之后。与此同时，重做登录/注册页的视觉层级和基础交互，使其与“地图优先”的品牌体验一致，但不得擅自改变现有鉴权后端、接口协议和账户体系。

这不是一次全站重构，也不是新增完整业务系统，而是一次范围严格受控的首页与登录注册页 MVP 视觉及交互升级。

## 二、Git 与原项目保护：先完成隔离，再开始分析

### 2.1 绝对禁止事项

- 禁止直接在当前稳定分支、主分支或原工作目录中改代码；
- 禁止对原工作区执行 `reset --hard`、`clean -fd`、自动 stash、自动提交、强制切分支或强制推送；
- 禁止覆盖用户尚未提交的文件；
- 禁止删除现有分支、标签、历史、数据库文件、环境变量文件或地图密钥；
- 禁止为了“方便”而重建项目、替换技术栈、替换地图供应商或重写认证体系；
- 禁止修改与本次范围无关的页面和业务逻辑；
- 禁止仅复制出一套失去 Git 历史的散乱目录后直接开发。

### 2.2 启动时必须记录

先只读执行并记录：

```bash
git status --short --branch
git branch --show-current
git rev-parse HEAD
git remote -v
git log -5 --oneline
```

将结果写入：

```text
docs/home-map-first/00-branch-safety-record.md
```

### 2.3 推荐的隔离结构

优先使用 Git Worktree，而不是直接复制整个含 `.git` 的目录：

```text
保护基线：backup/pre-home-map-first-20260819
开发分支：judge/home-map-first-auth-20260819
独立目录：仓库同级目录 ../yunyou-map-home-map-first-auth
```

若原工作区干净：

1. 从当前准确 HEAD 创建只读保护分支；
2. 从同一 HEAD 创建 `judge/home-map-first-auth-20260819`；
3. 在 `../yunyou-map-home-map-first-auth` 建立独立 Worktree；
4. 后续安装、运行、修改、测试、提交全部在新 Worktree 中进行；
5. 原工作目录保持原分支、原文件和原运行状态不变。

若原工作区存在未提交改动：

1. 不要在原工作区自动 stash、commit、reset 或 checkout；
2. 先导出包含 staged、unstaged 和 untracked 文件清单的安全备份；
3. 将差异以 patch 或等价的只读方式复制到独立 Worktree，使新支线尽可能复现“当前可见代码”；
4. 在安全记录中说明采用了什么方式、哪些文件被带入；
5. 若无法无损复现，暂停编码并明确报告，不得擅自处理原工作区。

创建完成后，再次证明隔离有效：分别输出原工作区和新 Worktree 的路径、当前分支及 HEAD，并确认所有后续操作目录都是新 Worktree。

## 三、先接管和审计现有项目，不得直接开写

在新 Worktree 中完成以下工作：

1. 识别项目框架、构建工具、包管理器、TypeScript/JavaScript 方案、CSS 方案、状态管理、路由、地图 SDK、后端/API、数据库和鉴权方案；
2. 查找首页、地图页、地图组件、地图数据、地点卡片、路线规划、社区、行程、登录、注册、用户状态、全局导航和设计 Token 的真实代码位置；
3. 检查现有地图是否已经具备平移、缩放、定位、点位、详情、导航、图层、搜索、路线、社区入口或行程入口；
4. 明确哪些能力可以直接复用，哪些只需要链接到现有页面，哪些当前并不存在；
5. 运行项目并用浏览器实际操作，不得只阅读文件名推断；
6. 采集改造前截图，至少包含：
   - 首页 1440×900；
   - 首页 1920×1080；
   - 首页 390×844；
   - 登录页桌面与移动端；
   - 注册页桌面与移动端；
7. 检查浏览器 Console、Network、地图 SDK 报错、环境变量缺失和现有功能异常，并区分“原有问题”与“本次新增问题”。

将结果整理为：

```text
docs/home-map-first/01-current-state-audit.md
```

审计必须包含：

- 当前首页首屏的视觉层级问题；
- 地图目前为什么不够突出；
- 哪些首屏元素挤占地图注意力；
- 当前地图组件是否可以直接放大复用；
- 登录注册页现状；
- 可复用组件清单；
- 风险与依赖；
- 本次严格不改动的区域。

## 四、进行有目的的案例调研，但不要照搬

调研 6—10 个优秀案例，覆盖以下四类：

1. 地图即首页、地图即主界面的产品；
2. 旅游发现与地点探索产品；
3. 路线规划与行程组织产品；
4. 地图社交、地点讨论、轨迹或打卡产品；
5. 与地图品牌结合良好的登录/注册页。

可关注高德地图、Google Maps、Mapbox 示例、Wanderlog、AllTrails、Komoot、Strava 等产品的相关界面，但不得直接复制视觉素材、文案或受版权保护的设计。

调研重点不是罗列产品，而是提炼：

- 地图在首屏中占据多少空间；
- 搜索、筛选、图层、定位、详情卡和路线按钮如何叠加而不挡图；
- 用户如何从“看地点”自然进入“导航、规划、社区”；
- 地图与内容卡片如何保持主次；
- 桌面端和移动端如何切换为抽屉、底部面板或全屏地图；
- 登录注册页如何延续地图品牌，但不干扰表单完成。

输出：

```text
docs/home-map-first/02-reference-research.md
```

每个参考案例都要写明“可借鉴点、不可照搬点、对本项目的具体启发”。

## 五、产品范围与核心用户任务

### 5.1 本次首页必须表达的五项核心能力

首屏必须让用户在不阅读长段落的情况下理解并进入以下能力：

1. **地图查看**：浏览景点、村落、服务点、活动和周边资源；
2. **地图导航**：从当前位置或选定起点前往目标地点；
3. **地图交互**：缩放、定位、筛选、切换图层、点击点位、查看详情；
4. **地图社交**：进入某个地点对应的动态、讨论、打卡或社区内容；
5. **地图规划**：将地点加入行程、创建路线或进入已有行程规划功能。

这些能力必须依托现有功能完成。若现有项目没有完整后端能力，可采用以下 MVP 方式，但不得伪造已上线功能：

- 链接到现有地图、社区或行程页面；
- 通过现有地点 ID 传递筛选上下文；
- 用本地草稿暂存“加入行程”，前提是项目已有相近机制；
- 对确实尚未实现的能力提供清晰的边界说明，不得制作点了无反应的假按钮。

### 5.2 本次不做

- 不新建完整地图社交后端；
- 不新建群聊、私信、好友关系或复杂社区系统；
- 不重做导航引擎；
- 不新增支付、订单、商户结算、会员体系；
- 不更换地图 SDK；
- 不重构数据库；
- 不新增复杂低代码地图编辑器；
- 不重做全站所有页面；
- 不为了评委效果制造假数据闭环或假接口成功状态。

## 六、首页“地图优先”重构要求

### 6.1 核心判断

现有截图中的地图本身已经具备一定内容和交互，但它被放在较深的位置，并被顶部较高导航、图片/来源信息、地图风格整行控件、卡片边距及其它视觉元素分散注意力。此次不能只是把地图容器高度增加几十像素，而要重新建立首页首屏的信息层级：

> 导航栏之后立即进入地图主舞台，地图是 Hero，Hero 不是地图之前的图片、横幅或长文案。

### 6.2 桌面端首屏结构

推荐结构如下，允许在理解现有代码后做等价优化：

```text
┌────────────────────────────────────────────────────────────┐
│ 精简导航栏：Logo / 首页 / 行程 / 地图 / 社区 / 我的 / 登录 │ 约 68–76px
├────────────────────────────────────────────────────────────┤
│                         可交互地图                           │
│  ┌──────────────────────┐              ┌───────────────┐   │
│  │ 搜索地点/路线/活动    │              │ 图层/定位/缩放 │   │
│  └──────────────────────┘              └───────────────┘   │
│                                                            │
│  [看地图] [去导航] [做规划] [看动态] [发打卡/进社区]        │
│                                                            │
│              选中点位卡：详情 / 导航 / 行程 / 社区          │
└────────────────────────────────────────────────────────────┘
│ 地图之后才出现核心能力说明、推荐地点、活动、影像和其它内容   │
```

具体要求：

- 地图直接位于主导航下方；
- 在 1440×900 视口中，无需滚动即可看到完整的地图主交互区；
- 地图应占据导航以下可视区域的大部分，建议 `min-height` 接近 `calc(100svh - 导航高度)`，同时设置合理最小值和最大值；
- 首屏地图建议覆盖至少 65% 的整个视口面积，且宽度不应再被过大的左右留白压缩；
- 保留适度圆角和品牌质感可以，但不要让地图看起来像普通内容卡片；
- 不要在地图之前放置大幅轮播图、来源说明条、长段宣传文案或大面积留白；
- 现有“用户提供实景影像 / 来源 / 官方了解更多 / 自动切换”等信息移到地图之后或合并为地图角落的轻量说明，不得抢占第一视觉层级；
- 现有“地图风格：标准地图、禅意皮肤、青山绿水、复古国风、3D 立体”不要继续独占一整行高度，改为地图内部的紧凑图层/皮肤控件、弹出菜单或横向小型切换器；
- 现有“显示与辅助”控制默认折叠为图标或小型面板；
- 保留地图版权、审图号及供应商归属信息，不得遮挡、删除或伪造；
- 修复截图中可能出现的左侧内容被裁切、右下浮层越界、地图控件与页面容器互相遮挡等问题。

### 6.3 首屏内容层级

地图上方或内部只允许保留少量高价值元素：

1. 一条主搜索框：支持搜索地点、景点、活动或路线，具体范围以现有数据为准；
2. 一组紧凑筛选：如景点、乡村、活动、服务、社区；
3. 五个核心能力入口：查看、导航、规划、互动/图层、社区；
4. 地图原生控制：缩放、定位、图层、全屏；
5. 一个选中地点详情卡或底部抽屉；
6. 一个清晰但不喧宾夺主的“打开完整地图”入口。

不要把长标题、五段说明、十几个按钮和多张卡片同时压在地图上。任何浮层在桌面端不应长期遮挡超过约 30%—35% 的地图可视面积。

### 6.4 地图点位与详情卡

复用现有点位和图片，不要伪造大量新景点。优化：

- 点位悬停、选中和聚合状态；
- 当前选中点位的视觉突出；
- 地图平滑移动到选中点位；
- 点位卡至少展示现有数据中的名称、类型、图片或摘要；
- 根据现有能力提供：
  - 查看详情；
  - 导航到这里；
  - 加入行程；
  - 进入该地点社区/动态；
- 无对应能力时不得显示无行为按钮；
- 卡片可收起，不应永久挡住地图；
- 空状态、图片缺失和数据错误要有稳健降级。

### 6.5 五类核心能力的交互要求

#### 地图查看

- 首页地图必须是真实交互地图，不是截图或纯装饰背景；
- 能平移、缩放、点击点位、查看地图信息；
- 默认视野应突出项目的核心景区或示范区域；
- 地图加载前提供骨架或轻量占位，不得白屏跳动。

#### 地图导航

- 选中地点后能进入现有导航流程；
- 优先复用现有站内导航或高德导航能力；
- 若需要定位权限，清楚处理授权、拒绝和不可用状态；
- 不得在没有路线能力时伪造路线已计算成功。

#### 地图交互

- 图层、地图皮肤、筛选和辅助功能应在地图内紧凑组织；
- 控件具有 Tooltip、选中态和键盘可达性；
- 触屏端控件尺寸不小于合理点击区域；
- 避免与地图原生手势冲突。

#### 地图社交

- 选中地点后，能够进入该地点关联的社区、动态、讨论或打卡入口；
- 若现有社区尚未支持地点筛选，可以通过查询参数、地点 ID 或预设筛选实现最小闭环；
- 首页只提供入口和少量预览，不在本次新建完整社交系统。

#### 地图规划

- 允许从选中地点进入行程页，或将地点加入现有行程草稿；
- 若已有“行程”页面，保留路由兼容并传递地点上下文；
- 若用户未登录，采用项目现有的登录拦截并保留返回路径；
- 不新建复杂多日算法规划器。

### 6.6 地图之后的首页内容

原首页有价值的内容不要粗暴删除，而是重新排序到地图之后：

1. 五项地图核心能力的简洁解释；
2. 推荐景点或精选路线；
3. 活动、乡村资源或服务点；
4. 地点社区/游客动态预览；
5. 实景影像、素材来源和官方说明；
6. 其它原有首页模块。

地图之后的内容必须服务于“继续探索地图”，卡片点击尽量回到对应点位、路线、行程或社区，不要形成与地图无关的信息孤岛。

### 6.7 导航栏调整

- 保留现有品牌、主要路由和用户入口；
- 桌面端导航建议控制在约 68—76px，减少当前过高的首屏占用；
- 首页仍可保持“首页”激活，但“地图”入口应具有较强识别度；
- 登录/注册按钮保留；
- 不在本次改动主导航的信息架构和业务含义；
- 导航可以使用轻度半透明或毛玻璃，但必须保证文字对比度和地图滚动时的可读性；
- 不使用过度花哨、持续干扰地图阅读的动画。

### 6.8 移动端要求

在 360—430px 宽度下：

- 首页首屏同样以地图为主，不得退化成先展示长文案；
- 顶部使用紧凑搜索与必要操作；
- 地点详情使用可拖动底部抽屉或底部卡片；
- 五项能力可组织为底部操作栏、横向滚动快捷入口或二级操作抽屉；
- 地图缩放、拖动和页面滚动不能互相锁死；
- 登录/注册入口清晰；
- 不出现横向溢出、按钮重叠、地图版权被遮挡或刘海安全区问题。

## 七、登录与注册页改造要求

用户原始要求停留在“然后就是登录注册页”。本轮先按以下合理边界执行：同时优化登录页和注册页的布局、视觉、表单体验及与地图品牌的关联，但不修改现有鉴权协议、数据库结构和账号业务规则。

### 7.1 先确认现状

- 确认当前是独立路由、弹窗还是同页切换；
- 确认现有登录方式：手机号、邮箱、用户名、验证码、密码或第三方登录；
- 确认注册字段、协议勾选、验证码、密码规则、后端响应和登录后跳转；
- 只展示真实可用的方式；
- 未配置的微信、QQ、短信、二维码或第三方登录不得伪造。

### 7.2 推荐桌面布局

采用地图品牌化但表单优先的双栏结构：

```text
┌──────────────────────────────┬───────────────────────────┐
│ 地图视觉区 / 项目价值说明     │ 登录或注册表单             │
│ 地点、路线、轻量动态标记       │ 标题 / 字段 / 校验 / 提交   │
│ “从地图开始探索”              │ 返回地图 / 先逛一逛        │
└──────────────────────────────┴───────────────────────────┘
```

要求：

- 左侧可以使用现有地图画面、低交互地图、路线纹理或项目实景素材，但不得让地图 SDK 重复初始化导致性能问题；
- 右侧表单保持安静、清楚、易完成；
- 登录和注册的切换逻辑遵循现有项目，不重复实现两套状态；
- 提供“返回首页地图”或“暂不登录，先逛地图”的明确入口；
- 若用户因“加入行程、收藏、发布动态”等操作被拦截到登录页，登录成功后应恢复原目标页或原操作上下文；
- 支持 `redirect` 或项目现有等价机制；
- 不在登录页塞入过多营销卡片。

### 7.3 表单体验

- 标签不能只依赖 placeholder；
- 具备清晰的必填、格式、密码、验证码和协议校验；
- 提交中禁用重复点击并显示加载状态；
- 错误信息靠近对应字段，同时提供表单级错误；
- 密码可显示/隐藏；
- 保留忘记密码、记住登录或验证码倒计时，但仅在原项目真实支持时显示；
- 使用语义化表单、正确 autocomplete、键盘提交和焦点状态；
- 协议链接保持可访问；
- 不在前端日志中输出密码、Token、手机号完整值或敏感响应。

### 7.4 移动端

- 取消强制双栏，使用单列卡片；
- 地图视觉退为顶部品牌区域或低对比背景；
- 表单在常见手机高度下可顺畅滚动；
- 键盘弹出后提交按钮和关键错误信息仍可访问；
- 适配安全区，不出现页面跳动或视口高度错误。

## 八、视觉与动效原则

- 延续现有云游地图的自然、乡村、文旅气质和已有品牌色，不另起一套不相干风格；
- 可继续使用米白、深绿、山水纹理等元素，但地图必须比装饰更醒目；
- 地图上的文字、控件和点位要保证清晰对比；
- 统一圆角、阴影、间距、按钮高度、图标线宽和交互状态；
- 动效只用于地图飞移、点位选中、抽屉展开、控件反馈和页面过渡；
- 避免持续漂浮、强视差、大面积粒子、自动轮播或抢夺地图注意力的动画；
- 尊重 `prefers-reduced-motion`；
- 不擅自下载不明授权字体或素材；
- 优先复用现有字体和图标体系；
- 所有新增图标风格一致，不混用多套图标库。

## 九、编码范围与工程约束

### 9.1 允许修改

- 首页页面及首页专用组件；
- 与首页地图展示直接相关的可复用组件；
- 登录页、注册页和认证页专用布局/样式；
- 为本次页面新增的局部样式、测试和文档；
- 在不破坏兼容性的前提下，对地图展示组件做小范围抽取或参数化。

### 9.2 原则上不得修改

- 其它业务页面布局；
- 后端接口协议；
- 数据库迁移；
- 用户角色与权限规则；
- 地图供应商和密钥机制；
- 全局路由名称；
- 全局 CSS reset 或大范围 Design Token，除非确有必要且证明无回归；
- 锁文件和依赖版本，除非现有依赖无法完成且理由充分。

### 9.3 工程要求

- 复用现有组件、类型、请求层、状态管理和设计 Token；
- 新样式尽量组件作用域化，避免污染其它页面；
- 不复制粘贴出第二套地图业务逻辑；
- 不在组件中硬编码密钥、用户信息或环境地址；
- 不使用大量绝对定位拼出只在一个分辨率好看的页面；
- 处理地图初始化和销毁，避免重复实例、事件泄漏和路由返回后白屏；
- 保持现有路由可直接访问和刷新；
- 失败、空数据、慢网、定位拒绝和图片加载失败均有降级；
- 保持地图供应商 Attribution 合规显示。

## 十二、验收标准

### 12.1 首页视觉验收

- 1440×900 打开首页，无需滚动即可明确看到大面积可交互地图；
- 主导航之外，没有其它大模块位于地图之前；
- 地图覆盖首屏主要面积，视觉权重明显高于轮播、说明条和推荐卡；
- 首屏能够在一次点击内进入查看、导航、规划、交互/图层、社区中的相应功能；
- 地图控件紧凑、层级清晰，不互相遮挡；
- 点位卡不长期遮挡超过约三分之一地图；
- 现有地图版权与审图号仍完整可见；
- 原首页重要内容仍存在，但已经位于地图之后；
- 375、390、768、1024、1440、1920 宽度无横向溢出和关键控件重叠。

### 12.2 地图功能验收

至少验证：

1. 地图加载与失败降级；
2. 平移和缩放；
3. 定位授权、拒绝和失败；
4. 点位悬停/点击/选中；
5. 地点详情；
6. 图层或皮肤切换；
7. 进入导航；
8. 加入或进入行程规划；
9. 进入地点社区/动态；
10. 返回首页后地图状态不异常；
11. 路由切换后地图实例不重复、不泄漏。

### 12.3 登录注册验收

- 登录和注册使用现有真实接口；
- 正常、错误、加载和禁用状态完整；
- 不会重复提交；
- 密码与敏感信息不泄漏到日志；
- 登录成功后保持原有跳转，并支持返回被拦截的地图/行程/社区目标；
- “先逛地图”可正常返回首页；
- 移动键盘和窄屏不遮挡关键操作；
- 未配置的第三方登录不显示；
- 表单可通过键盘完成并具备清晰焦点。

### 12.4 质量验收

- 新代码不引入 Console Error；
- Network 中无由本次改动造成的持续 404/500；
- 构建、类型检查、Lint 和现有测试通过；
- 不产生地图重复初始化警告；
- 不破坏其它路由；
- 原工作区和稳定分支未被修改；
- `git diff` 范围与本次需求一致；
- 不存在仅有 UI、点击无行为的核心按钮；
- 不使用“已完成”描述掩盖未实现或不可测试的能力。
