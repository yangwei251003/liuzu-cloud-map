# 一、你的身份与总任务

你现在首次接手一个已经存在、已经能够运行的“云游地图”网站项目。你不是来推倒重写，也不是来只做三张静态演示页面。你要作为本项目的总负责人，统筹并实际承担以下角色：

- 项目接管负责人 / 仓库审计负责人
- 产品经理与用户研究负责人
- 旅游地图与县域文旅平台解决方案架构师
- UX/UI 设计负责人
- 前端、后端与数据架构负责人
- Git 分支与集成负责人
- 测试、浏览器验收与演示交付负责人

本轮任务是为“面向评委的阶段性演示”制作一个**完全隔离、可回退、不影响现有稳定代码**的三端 MVP。三端分别为：

1. **游客端：云游地图**
2. **网站管理与内容创作端：云游 Studio**
3. **商户、企业、村集体与文旅资源入驻端：云游伙伴中心**

这三个端不是三个互不相关的网站模板，而必须围绕同一套文旅资源数据形成一个能实际演示的闭环：

> 商户提交景点、门店、服务或活动资源  
> → 管理与内容创作端审核、修改地图位置、预览并发布  
> → 游客端立即发现该资源，查看详情、收藏并发起导航  
> → 游客行为形成基础数据，回到管理端和商户端展示

你必须先完成项目审计、竞品调研、PRD、信息架构、设计规范、技术设计、数据与接口设计、分支计划、测试计划；文档自检通过后，再自动开始实现，不要只停留在方案阶段。

# 二、项目背景与产品定位

“云游地图”不是普通景点列表，也不是单一地图皮肤展示项目。它的长期定位是：

- 以景区地图和游客服务完成用户冷启动；
- 逐步接入景区、村集体、合作社、农户、民宿、餐饮、非遗传承人、活动组织者等县域资源；
- 通过茶艺、讲座、采摘、非遗体验、研学、节庆活动等内容吸引游客与入乡青年；
- 后续扩展青年旅居、内容创作、地图社交、打卡分享与县域持续运营；
- 最终形成面向游客、景区、村集体和经营主体的数字文旅服务平台。

本次只实现评委可清楚理解、可稳定演示的第一版 MVP，不要一次性把长期规划全部塞入三端。

本轮产品对外叙事统一为：

> **云游地图把分散的县域文旅资源变成可提交、可审核、可落图、可发现、可导航、可运营的数字化资源。**

# 三、最高优先级安全规则

以下规则不可违反：

1. **绝对禁止在当前稳定分支或原项目目录上直接进行大规模修改。**
2. 在修改任何业务文件之前，先记录：
   - 原项目绝对路径；
   - 当前分支名；
   - 当前 HEAD Commit SHA；
   - `git status`；
   - 已配置 remote；
   - 当前可运行命令、构建命令和测试命令。
3. 如果原工作区存在未提交、未跟踪或被忽略但业务必需的文件：
   - 不得 `git reset --hard`；
   - 不得 `git clean -fd`、`git clean -fdx`；
   - 不得覆盖、删除、丢弃或擅自 stash 用户文件；
   - 先创建完整的同级目录副本，并只在副本中工作；
   - 保留 `.git`、源码、配置模板、公共资源和当前本地改动；
   - 可排除 `node_modules`、`.next`、`dist`、`build`、缓存等可重新生成目录；
   - 在审计文档中记录副本路径与排除项。
4. 如果工作区干净且全部必要代码已提交：
   - 创建只读快照 Tag；
   - 使用独立集成分支和 Git Worktree；
   - 原稳定分支保持不变。
5. 禁止 force push，禁止改写原分支历史，禁止删除远程分支，禁止合并回 `main`、`master`、`develop` 或原稳定分支。
6. 禁止无目的地升级框架、地图 SDK、UI 库、构建工具或全部依赖。
7. 禁止为追求“看起来高级”而替换当前地图引擎、认证系统、数据库或路由体系。
8. 禁止把 API Key、数据库密码、令牌或真实商户隐私信息写入代码、文档、截图或提交。
9. 所有演示按钮必须有真实可验证的行为。不得出现无响应按钮、假成功提示或只有外观没有状态变化的流程。
10. 对缺少外部 API、短信、支付、邮件、对象存储等凭证的功能，使用清晰隔离的 Demo Adapter 或本地持久化方案，并在界面与文档中标注“演示环境”，不得伪装成真实生产接入。
11. 除非遇到必须由用户提供的外部密钥、域名控制权或不可替代数据，否则不要反复询问。优先选择最低风险、可回退、可替换的默认方案并记录假设。

# 四、Git 分支、项目副本与 Worktree 结构

先自动检测真实稳定分支名，不要假设一定叫 `main`。

建议结构如下；若同名已存在，追加日期或序号：

```text
<当前稳定分支，保持不动>
└── judge/three-portals-mvp
    ├── judge/portal-visitor-mvp
    ├── judge/portal-studio-mvp
    └── judge/portal-partner-mvp
```

同时创建：

```text
snapshot/pre-three-portals-20260819
```

执行原则：

1. `snapshot/pre-three-portals-20260819` 只用于记录原始基线。
2. `judge/three-portals-mvp` 是总装、共享基础和最终评委演示分支。
3. 先在总装分支完成并提交以下“共享基础”：
   - 三端路由壳；
   - 共享设计 Token；
   - 角色与权限模型；
   - 共享领域模型；
   - Demo 数据仓库/现有后端适配层；
   - 演示模式与重置机制；
   - 三端入口页；
   - 基础测试配置。
4. 共享基础提交完成后，再从同一个 Commit 创建三条功能分支和三个独立 Worktree。
5. 三条功能分支的主要文件所有权：
   - 游客端：游客端路由、页面、组件、游客 E2E；
   - Studio：管理创作端路由、页面、组件、审核与发布 E2E；
   - Partner：商户端路由、页面、组件、入驻与提交 E2E。
6. 共享领域模型、根配置、全局依赖、数据库迁移和跨端 API 只允许由“总装/共享负责人”修改，避免三个代理并行改同一文件。
7. 每条功能分支完成后先自测，再依次合并到 `judge/three-portals-mvp`；每合并一条都重新执行构建、单测和跨端 E2E。
8. 最终只交付 `judge/three-portals-mvp`，不自动合并回原稳定分支。
9. 最终报告中必须给出：
   - 原始 Commit SHA；
   - 快照 Tag；
   - 四条新分支；
   - 每条分支主要 Commit；
   - 原稳定分支未变化的核验证据。

# 五、Antigravity 多代理组织方式

在安全副本或总装分支中创建并维护：

```text
.agents/
├── agents.md
├── skills/
│   ├── repo-audit.md
│   ├── product-research.md
│   ├── prd-and-scope.md
│   ├── ux-ui-system.md
│   ├── git-safety.md
│   ├── shared-architecture.md
│   ├── portal-implementation.md
│   ├── browser-qa.md
│   └── demo-handoff.md
└── workflows/
    └── three-portals-mvp.md
```

在 `agents.md` 中定义以下代理及边界：

1. **Lead / Architect**
   - 负责总计划、技术决策、共享模型、分支、集成和最终交付。
2. **Repository Auditor**
   - 只审计现有代码、运行现状、依赖、路由、后端、地图、数据库和风险；早期不改业务代码。
3. **Product Researcher**
   - 负责三端用户、竞品、需求、JTBD、MVP 边界和评委叙事。
4. **UX/UI Designer**
   - 负责信息架构、用户流程、线框、设计系统、响应式与交互规范。
5. **Shared Platform Engineer**
   - 负责共享领域模型、角色权限、数据访问、Demo 模式、共享组件和路由壳。
6. **Visitor Portal Engineer**
   - 只负责游客端范围。
7. **Studio Portal Engineer**
   - 只负责管理与内容创作端范围。
8. **Partner Portal Engineer**
   - 只负责商户资源入驻端范围。
9. **QA / Browser Verification**
   - 负责测试矩阵、浏览器录制、截图、回归和问题清单。

并行规则：

- 审计、研究和文档阶段可并行；
- 架构、数据模型、路由、状态机和设计 Token 冻结前，不得并行写三端业务代码；
- 共享基础完成后再启动三个门户代理；
- 不得让多个代理同时改根配置、共享模型或同一页面；
- 每个代理必须输出可核验 Artifact，而不是只口头宣称完成。

# 七、第二阶段：三端用户与案例调研

必须使用浏览器调研当前可访问的真实案例，不能只凭常识生成泛泛结论。

## 7.1 调研数量与类型

每个端至少研究 3 个高质量案例，总数不少于 10 个；每端尽量覆盖：

- 一个中国本地或中文平台；
- 一个国际成熟产品；
- 一个地图、CMS、商家管理或垂直旅游产品。

建议调研方向，不要求机械照搬：

### 游客端

- 地图发现、附近探索、收藏与路线产品；
- 景区导览、文旅地图、徒步路线产品；
- OTA 或目的地内容产品。

可参考的产品类型包括：高德地图、Google Maps、携程目的地、马蜂窝、AllTrails、Komoot、成熟景区数字导览等。

### 管理与内容创作端

- Mapbox Studio、ArcGIS Experience Builder 等地图数据与发布工具；
- Strapi、Sanity、Contentful 等内容管理产品；
- 运营审核后台、活动发布后台、推荐位编排后台。

### 商户入驻端

- Google Business Profile；
- 美团、携程、抖音生活服务等商户入驻或经营后台；
- Airbnb Host、Booking Partner 等资源发布与状态管理产品；
- 文旅活动发布、合作社或本地生活服务入驻流程。

## 7.2 调研维度

对每个案例记录：

- 产品与来源链接；
- 调研日期；
- 目标用户；
- 首次进入路径；
- 导航结构；
- 最核心任务；
- 表单或编辑流程；
- 地图交互方式；
- 审核与状态反馈；
- 信任机制；
- 空状态、错误状态与帮助机制；
- 移动端与桌面端差异；
- 值得借鉴的模式；
- 不适合云游地图的做法；
- 对本项目 MVP 的具体启示。

严禁直接复刻竞争产品界面、文案或品牌视觉。只提炼信息架构、交互模式和业务机制。

## 7.3 输出调研文档

创建：

```text
docs/judge-mvp/01-benchmark-research.md
```

使用对比矩阵，不要只写长篇散文。最后必须形成：

- 游客端 5 条核心设计原则；
- Studio 5 条核心设计原则；
- Partner 5 条核心设计原则；
- 三端共用的 5 条平台原则；
- 本轮明确不做的功能清单。

# 八、产品核心闭环与评委演示故事

本轮所有功能优先服务于以下“黄金演示路径”：

## 8.1 演示角色

- 一个已通过基础入驻审核的演示商户/合作社账号；
- 一个管理与内容创作账号；
- 一个匿名游客或游客演示账号。

## 8.2 演示数据

优先复用当前项目已有地点、图片和区域数据。若必须补充，创建明确标记为“演示数据”的本地文化内容，例如：

- 茶园、合作社、民宿、农家乐、非遗工坊；
- 茶艺体验、采摘活动、讲座、研学或村落导览；
- 停车场、游客中心、卫生间、观景点等服务点。

不得伪造真实企业资质、真实用户评论或真实交易数据。

## 8.3 黄金路径

1. 评委进入 `/judge` 演示入口；
2. 打开“云游伙伴中心”；
3. 使用演示商户账号创建一个“茶艺体验”或同类活动；
4. 选择关联地点，在地图上确认位置；
5. 填写时间、价格说明、人数、联系方式和图片；
6. 预览并提交；
7. 切换到“云游 Studio”；
8. 在待审核队列看到刚提交的内容；
9. 打开详情，检查资料；
10. 必要时调整地图点位、分类、标签或推荐图；
11. 填写审核意见并批准发布；
12. 切换到游客端；
13. 在地图、搜索或“今日体验”中看到刚发布的活动；
14. 打开详情、收藏；
15. 查看路线预览并发起导航；
16. 产生“查看、收藏、导航启动”基础事件；
17. 回到 Studio 或 Partner 查看基础数据变化。

这是验收优先级最高的跨端流程。三端功能再多，只要这条路径不稳定，本轮就不能判定完成。

# 十、游客端 MVP

## 10.1 核心用户

- 第一次到访的游客；
- 正在景区或乡村现场的游客；
- 想快速安排半日或一日路线的人；
- 对本地文化体验、活动和服务点感兴趣的人。

## 10.2 核心需求

游客最关心的不是复杂账号体系，而是：

- 我现在在哪里；
- 附近有什么值得去；
- 这个地点是否适合我；
- 开放时间、服务和活动是否可信；
- 怎么到达；
- 能否先收藏，少做决策。

## 10.3 P0 功能

### A. 地图首页

- 沿用并优化当前地图，不重新替换地图引擎；
- 定位按钮与定位失败回退；
- 搜索地点、活动和服务点；
- 分类筛选：景点、体验、餐饮、住宿、服务等；
- 服务图层：停车、卫生间、游客中心、医疗/应急等，按已有数据能力取舍；
- 地图标记与卡片联动；
- 点击标记出现精简底部卡片或侧边卡片；
- 清晰的“查看详情”“收藏”“去这里”主操作；
- 支持刚由 Studio 发布的新资源及时出现。

### B. 发现页

- 推荐地点；
- 当前可参加或近期活动；
- 按距离、类别或推荐排序；
- 不做复杂个性化算法；
- 允许通过筛选快速回到地图结果。

### C. 地点/活动详情

至少展示：

- 标题、图片、简短介绍；
- 地图位置；
- 标签；
- 开放时间或活动时间；
- 价格说明，没有价格则明确“免费”或“现场咨询”；
- 服务设施；
- 联系方式或预约说明；
- 主办方/商户；
- 收藏；
- 路线预览和导航入口；
- 内容更新时间与演示数据标记。

### D. 收藏与轻行程

- 游客无需注册即可收藏；
- 本地持久化，刷新后仍存在；
- 可查看收藏列表；
- 可从收藏条目回到地图与详情；
- 第一版不做复杂自动排程、多日行程优化或 AI 规划。

### E. 导航

- 优先复用项目已有导航或路线能力；
- 若已有路线 API，展示距离、预计时间和路线；
- 若没有可用路线 API，至少提供：
  - 当前位置/指定起点到目标点的路线预览；
  - 调用现有地图能力或外部地图 Deep Link；
  - 清晰错误和无定位回退；
- 不承诺第一版实现完整语音导航、离线导航或实时交通。

## 10.4 游客端设计要求

- 移动优先；
- 地图应是视觉主体；
- 使用底部导航或当前项目已有移动导航；
- 地图上的浮层不能遮住主要目标；
- 详情采用轻量卡片、底部抽屉或沉浸式详情；
- 保留项目现有地域文化与视觉特色，但不要过度堆叠装饰；
- 页面必须适配 390×844、768px 宽度和 1366×768 评委演示屏；
- 所有定位、加载、无结果、网络失败、无图片状态均有设计。

## 10.5 游客端暂不做

- 新增大型地图社交系统；
- 实时群聊；
- 用户关注关系；
- 完整 UGC 审核；
- 复杂会员系统；
- 支付、订单与退款；
- AI 自动生成全程路线；
- 多语言；
- 离线地图包。

如果现有项目已经有部分社交或其他功能，保留兼容，不要删除；本轮不扩建。

## 10.6 游客端验收

- 未登录用户能在 3 次主要操作内找到一个目标地点并进入导航；
- 发布后的活动能被搜索或在推荐区看到；
- 收藏刷新后仍存在；
- 地图标记、卡片和详情数据一致；
- 移动端无横向溢出；
- 无死按钮和控制台报错。

# 十一、管理与内容创作端 MVP：云游 Studio

## 11.1 核心用户

- 项目管理员；
- 景区工作人员；
- 内容运营人员；
- 地图内容编辑者；
- 后续可能扩展的网站开发或高级创作者。

第一版把“管理、开发者、创作”收敛成一个统一工作台角色，不做复杂低代码开发平台。

## 11.2 核心需求

- 快速知道当前有什么需要处理；
- 高效审核商户提交；
- 保证地点、图片、分类、时间和联系方式质量；
- 准确把资源放到地图上；
- 发布前看到游客端效果；
- 控制哪些内容被推荐；
- 出现问题时能追踪谁在何时做了什么。

## 11.3 P0 功能

### A. 总览仪表盘

至少展示：

- 待审核数量；
- 已发布地点/资源数量；
- 进行中或即将开始的活动数量；
- 最近新增内容；
- 最近审核记录；
- 基础游客行为：查看、收藏、导航启动；
- “继续处理待审核”的明确入口。

避免为了好看添加没有意义的大量图表。数据必须来源于真实 Demo 数据仓库、现有后端或事件记录。

### B. 审核中心

- 待审核、需修改、已通过、已拒绝筛选；
- 搜索商户、资源名、类别；
- 列表与详情；
- 查看提交资料、图片、位置、时间、价格和联系方式；
- 查看游客端预览；
- 审核操作：
  - 通过并发布；
  - 通过但暂不推荐；
  - 要求修改；
  - 拒绝；
- “要求修改”和“拒绝”必须填写原因；
- 状态变更要生成审核记录；
- 商户端能看到审核结果和意见。

### C. 地点与活动内容管理

- 查看已发布和草稿内容；
- 新建、编辑、发布、下架；
- 分类与标签；
- 关联组织/商户；
- 图片与摘要；
- 开放时间或活动时间；
- 服务信息；
- 预览游客卡片和详情；
- 第一版不做大批量 Excel 导入和复杂内容版本树。

### D. 地图内容编辑

采用“地图 + 属性面板”模式：

- 搜索或选择一个资源；
- 在地图上查看当前点位；
- 点击或拖动确定经纬度；
- 编辑类别、图标或标记类型；
- 保存草稿；
- 预览游客端标记和卡片；
- 发布后游客端能读取；
- 不做完整 GIS、复杂图层分析、空间运算或地图样式引擎重写。

### E. 推荐位编排

第一版只做轻量能力：

- 将已发布地点/活动标记为“首页推荐”；
- 设置简单排序或推荐优先级；
- 预览游客端推荐卡片；
- 不做完整拖拽页面搭建器、组件市场或多页面低代码平台。

### F. 最小审计记录

至少记录：

- 操作人；
- 时间；
- 对象；
- 旧状态与新状态；
- 审核意见；
- 发布/下架动作。

## 11.4 Studio 设计要求

- 桌面优先，兼顾平板；
- 使用清晰侧边栏和顶部上下文；
- 数据密度适中，避免游客端式大图占满后台；
- 审核详情建议采用双栏：资料/预览 + 审核操作；
- 地图编辑建议采用地图与表单分屏；
- 状态颜色和文案一致；
- 高风险操作有确认；
- 成功后有明确反馈；
- 空队列、无权限、加载失败均有状态；
- 不做“套模板式通用后台”，要保留云游地图品牌与地域文化细节。

## 11.5 Studio 暂不做

- 完整站点可视化搭建器；
- 代码在线编辑器；
- Git、CI/CD 管理；
- 多级组织与极细权限；
- 工作流自定义引擎；
- 大规模 GIS 处理；
- 高级 BI；
- 自动化内容生成与审核；
- 多租户计费。

## 11.6 Studio 验收

- 能看到 Partner 刚提交的内容；
- 能完整审核并写入审核意见；
- 能调整点位；

# 十二、商户资源入驻端 MVP：云游伙伴中心

## 12.3 P0 功能

第一版字段控制在必要范围：

- 主体名称；

- 联系人；
- 手机或联系方式；
- 简介；
- 所在区域；

- 保存草稿；
- 提交审核；

### C. 商户工作台

至少展示：

- 资料完整度；
- 我的地点/资源；
- 我的活动；
- 草稿；
- 审核中；
- 需修改；
- 已发布；
- 最近审核反馈；
- 快速新建入口。

### D. 资源/活动提交向导

使用分步表单，建议步骤：

1. 选择类型：地点、服务、活动；
2. 基础信息：名称、简介、类别、联系人；
3. 位置：地址、地图选点、关联已有地点；
4. 经营/活动信息：开放时间、活动时间、价格说明、人数、预约方式；
5. 图片与补充说明；
6. 游客端预览；
7. 保存草稿或提交审核。

要求：

- 自动保存或明确保存草稿；
- 字段校验清楚；
- 地图选点直观；
- 上传失败可重试；
- 提交前有完整预览；
- 提交后不能直接修改已审核版本，必须按状态进入修订；
- 不允许商户自己把内容设为已发布。

### E. 审核状态与修订

状态至少包括：

```text

→ 已提交/审核中
→ 需修改
→ 重新提交/审核中
→ 已通过
→ 已发布

另有：已拒绝、已下架
```

页面必须展示：

- 当前状态；
- 状态时间线；
- 审核意见；
- 哪些字段需要修改；
- 编辑并重新提交；
- 已发布内容的游客端入口。

### F. 基础表现

仅做真实可解释的基础指标：

- 游客端查看次数；
- 收藏次数；
- 导航启动次数；
- 统计周期或更新时间；
- 无数据时给出合理空状态。

第一版不做复杂漏斗、预测、经营诊断或虚假增长建议。

## 12.4 Partner 设计要求

# 十四、数据与 API 实现策略

1. 优先复用现有 API、数据库和状态管理。
2. 不要在 React/Vue 页面中散落硬编码 Demo 数据。
3. 抽象统一的数据访问层，例如：
   - `PlaceRepository`
   - `ActivityRepository`
   - `SubmissionRepository`
   - `MetricsRepository`
4. 根据当前项目情况实现：
   - 真实后端 Adapter；
   - Demo Adapter；
   - 或二者可切换。
5. 推荐使用环境变量或配置开关：
   - `DEMO_MODE=true`
   - `ENABLE_JUDGE_PORTALS=true`
6. Demo 模式要求：
   - 三端共用同一数据源；
   - 操作可持久化；
   - 页面刷新后状态仍存在；
   - 提供“恢复初始演示数据”；
   - 使用稳定 ID；
   - 重置后黄金路径可重复演示。
7. 若三端在同一 Origin 下，允许使用现有后端、IndexedDB 或 localStorage 作为 MVP 持久化；但必须封装在 Repository 中，不能让页面直接依赖存储细节。
8. 若已有服务端，优先实现真实共享状态。
9. 上传可采用当前上传服务；缺少服务时使用演示文件预览与本地元数据，不上传真实敏感材料。
10. 导航、地图和图片功能必须有无凭证回退。
11. 不进行破坏性数据库迁移。所有迁移必须向后兼容、可回滚，并记录在技术文档。

# 十六、UI/UX 与视觉设计要求

## 16.1 总体原则

- 先读取并继承当前项目的品牌、Logo、颜色、字体、地图皮肤和地方文化视觉；
- 不要把三端做成三个毫无关系的模板；
- 三端共享基础 Token、图标、圆角、阴影、状态色和品牌资产；
- 三端可以有不同的信息密度和交互模式；
- “好看”必须建立在任务清楚、层级明确、状态完整和数据可信上；
- 不追求无意义的炫技、重 3D、大量粒子或阻碍操作的动画；
- 不使用 Lorem Ipsum 和空洞占位文案；
- 不随意下载来源不明的字体、图标或图片；
- 新增字体或素材必须确认许可证并本地化管理；
- 运行时不能依赖不稳定的外部图片链接。

## 16.2 三端视觉差异

### 游客端

- 沉浸、轻快、在地感；
- 地图和实景内容为主；
- 卡片轻量；
- 移动底部抽屉；
- 地图标记与内容卡联动；
- 适度使用自然纹理、地方图形和微动效。

### Studio

- 专业、克制、清晰；
- 信息密度高于游客端；
- 桌面侧栏；
- 表格、筛选、状态、预览和地图分屏；
- 保留品牌色作为关键操作和状态强调；
- 避免整页大图和过度玻璃拟态影响可读性。

### Partner

- 温暖、可信、友好；
- 清晰步骤条；
- 较大输入区域；
- 明确帮助和示例；
- 状态时间线；
- 价值说明与行动入口；
- 不制造“复杂政府系统”或“强销售后台”的压迫感。

## 16.3 交互与动效

- 页面/抽屉/弹窗过渡通常控制在 150–300ms；
- 标记选中、卡片展开、状态改变有适度反馈；
- 支持减少动态效果；
- 避免动画阻断点击；
- 表单保存、提交、审核、发布都有明确处理中、成功、失败状态；
- 导航发起前避免误触；
- 高风险操作二次确认。

## 16.4 可访问性与响应式

- 键盘可访问；
- 可见焦点；
- 合理语义标签；
- 图片 alt；
- 表单 label；
- 状态不只依赖颜色；
- 正文字号和行高适合中文阅读；
- 适配至少：
  - 390×844；
  - 768×1024；
  - 1366×768；
  - 1440×900；
- 投影或笔记本演示时，关键操作不应被折叠到难找的位置。

# 十九、代码实现规范

1. 先遵循现有项目代码风格和目录规范。

12. 所有状态转换由共享规则校验。

14. 不修改与本任务无关的业务。
15. 不删除现有功能。确需隐藏时使用功能开关或新入口，不做破坏性移除。
16. 保留旧路由兼容。
17. 代码提交要小而清晰，例如：
    - `docs(judge): add audit and three-portal PRDs`

# 二十三、异常情况处理

1. **当前项目无法运行**
   - 先记录基线错误；
   - 优先修复最小阻断；
   - 不借机重写；
   - 在报告中区分原有问题和本轮修复。
2. **缺地图 Token**
   - 使用现有本地底图、Mock 地图或可用回退；
   - 保留真实地图 Adapter；
   - 文档说明如何接入。
3. **缺后端**
   - 使用共享 Demo Repository；
   - 保证三端同源、持久化和可重置；
   - 不把数据散落在组件。
4. **缺认证**
   - 实现仅用于 Demo 的角色选择；
   - 明确隔离；
   - 生产默认关闭；
   - 技术文档写出真实认证接入点。
5. **现有代码耦合严重**
   - 采用外层 Route/Layout 和 Adapter 增量接入；
   - 不做全项目重构。
6. **竞品页面不可访问**
   - 记录失败；
   - 更换同类高质量来源；
   - 不凭空编造功能。
7. **时间或上下文不足**
   - 优先完成黄金路径和 P0；
   - 删除 P1，不牺牲测试、权限和可回退性；
   - 在 `IMPLEMENTATION_STATUS.md` 中如实记录。

# 二十五、最终决策原则

当需求存在多种实现方式时，按以下顺序决策：

1. 不影响现有项目；
2. 能完整演示跨端闭环；
3. 复用当前能力；
4. 代码可维护、数据一致；
5. 用户任务简单；
6. 评委能快速理解；
7. 视觉精致；
8. 功能数量。

本轮最重要的不是“每端页面很多”，而是：

> **一个商户资源能够被提交、审核、落图、发布、发现和导航；三端各自解决真实用户的基本问题，并且整个过程稳定、清楚、好看、可重复演示。**

现在开始：先执行安全检查和现状审计，产出全部关键文档并完成交叉自检，然后进入共享基础和三端 MVP 实现，最后完成浏览器验证、黄金路径录制和交付报告。
