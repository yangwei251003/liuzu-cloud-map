# 景区级智能导航系统架构与实施计划

更新时间：2026-08-16（Asia/Shanghai）

## 1. 交付定位与当前结论

云游地图采用“公开道路导航”和“景区内部导航”双域架构：公开道路、公开 POI 与外部驾车/步行计算交由高德；景区内部逐向导航只读取管理方发布、现场复走、许可已清、仍在有效期内的 WGS84 路网和运营快照。两类数据不得互相冒充或静默拼接。

当前已经形成可运行的正式导航软件闭环：

- `src/lib/directed-route-engine.ts` 支持最快、最短、观光三种确定性策略，继续执行单向、封路、无障碍、版本和有效期约束；
- 索道与观光车按独立交通段处理，默认不参与路线；游客显式选择后，只有服务名称、上车/等候/乘坐时长、HTTPS 班次依据和当前运营开放状态均完整时才能规划；
- `src/lib/route-network.ts` 支持有证据引用的道路类型、难度和观光评分；
- `src/lib/route-operational-state.ts` 支持运营方发布的拥堵/天气影响与耗时倍率；
- `/api/v1/route-plans` 接受封闭的策略与偏好契约，拒绝客户端注入任意边权；
- `/guide` 新增正式内部导航规划器，具备加载、空、错误、未发布和成功状态；浏览器已授予定位权限时，正式快照加载后自动执行一次高精度节点匹配；权限仍为询问时保留手动按钮而不自动弹窗；精确坐标不保存或上传；
- `005_scenic_navigation_intelligence.sql` 增加版本化路由权重、导航会话和不含连续 GPS 的历史审计结构。
- 前台导航运行时具备路线投影、剩余距离/时间、转向提示、10 秒样本新鲜度、定位跳点过滤、三点偏航滞回、三点加 10 秒到达确认、暂停/恢复/退出，以及 15 秒和页面恢复时的运营版本复核；
- 转向只发生在正式 `RoadEdge` 边界，边内折线造型点仅用于几何跟随；剩余距离和进度按“当前边剩余 + 后续正式边”计算，不按整条折线比例猜测；
- 路线投影使用“设备实际移动 + 前后定位精度 + 15 米缓冲”的进度连续性包络；重叠几何从最早安全进度开始，连续三次远端分支跳变先停旧指令再重算；连续三次可靠反向进度显示掉头警告，回到最远已达进度附近后恢复；
- 正式地图按匹配线段和线段内比例精确拆分路线：灰线表示最后确认已走部分，蓝线表示剩余部分，交通虚线仅保留未完成服务段；无有效匹配时不宣称已走进度，整条路线保持蓝色；
- 地图相机在可靠定位时默认跟随；游客拖动、缩放或旋转即进入手动浏览，GPS 更新不再抢回视野；剩余路线总览只使用未完成几何，必须显式“回到当前位置”才恢复跟随，低精度/停止状态不移动相机；
- 页面切后台、离开或冻结时立即停止连续定位并清除自动重算最近定位；回前台先复核完整正式快照，版本一致也必须由游客显式确认后才重新等待新鲜定位；
- 地图以设备内临时 WGS84 点绘制浏览器报告的定位精度圈，可靠、待确认和停止状态分别显示不同颜色，不可靠时隐藏旧方向箭头；精度圈不上传、不缓存；
- 正式 MapLibre 路线层显示蓝色路线、起终点、当前位置和方向箭头，不加载候选 GIS 作为兜底；
- 离线包采用完整正式发布链、ECDSA P-256 签名、规范化清单 SHA-256、唯一资产角色、逐资产流式 SHA-256/字节/类型校验、隔离候选缓存、原子活动登记和最多 72 小时有效期；Service Worker 只服务已验签登记中的精确路径并支持 PMTiles Range。当前没有正式生产包，因此仍显示本机无可用包；
- 好友同行具备建队、哈希邀请、显式开始/停止共享、最多 8 小时会话、最多 2 分钟单点覆盖快照、成员鉴权以及距离/方向显示，不形成轨迹；
- “AI 智能游览路线”先在本机把自然语言转成游客确认的时间、兴趣、节奏和同行约束，再由正式路网上的确定性多站动态规划生成路线；原始文字、年龄与坐标不进入服务端；
- 沿途推荐同时要求正式游览证据、前方 120 米几何走廊和本次路线 traversal 拓扑成员关系；地点社区读取按景区租户隔离，只暴露绑定当前正式 POI 的 24 小时审核摘要，不发送游客 GPS；
- 候选地图后台覆盖入口、道路、景点、设施、推荐路线和边界，支持道路类型、难度、观光评分、耗时系数、无障碍和游览属性；候选草稿与正式发布仍严格隔离。

当前六祖镇正式内部路网仍未发布，因此游客端会诚实显示“正式内部导航尚未开放”。这不是代码缺失，而是 RSK-002、RSK-018、RSK-023 的失败关闭结果。

## 2. 技术选型

| 层 | 选择 | 原因 |
| --- | --- | --- |
| Web/H5/PWA | Next.js 16 + React 19 + TypeScript | 复用现有应用、服务端 Route Handler、客户端定位叶组件和 PWA；避免新建并行技术栈。 |
| 主题地图 | MapLibre GL JS + PMTiles | 开源、可定制矢量样式、支持本地/对象存储瓦片；标准皮肤与禅意皮肤共享同一正式几何。 |
| 中国公共道路 | 高德 Web JS/Web Service/URI | 负责公开 POI、公开道路显示和外部导航；不生成景区内部拓扑。 |
| 空间数据库 | PostgreSQL + PostGIS | WGS84 几何、版本化路网、空间索引、距离校验、运营快照和审计事务。 |
| 服务端 | Next.js Node.js Route Handlers | 与现有身份、分享、治理和 PostGIS 访问保持同一部署单元；后续可独立拆出路由服务。 |
| 路径算法 | 确定性有向 Dijkstra | 当前路网规模足够、便于审计和稳定复现；支持非负动态权重。路网达到十万级边后再引入带可采纳启发式的 A*。 |
| 管理端 | MapLibre + Terra Draw | 现有地图草稿编辑器可继续扩展节点、边、入口、风险区、证据和发布工作流。 |

没有选择 Mapbox GL JS，是因为现有项目已经使用 MapLibre，且当前不应新增长期付费或供应商锁定；没有选择 Leaflet，是因为矢量样式、PMTiles、2.5D 和大规模图层交互需求更适合 WebGL 地图；没有选择 Java，是因为当前负载与团队代码基线无需承担第二套运行时和部署复杂度。

## 4. GPS 定位状态机

游客端定位不是一个布尔值，而是以下状态：

| 状态 | 进入条件 | 产品行为 |
| --- | --- | --- |
| `IDLE` | 默认、暂停、退出、页面后台 | 不请求定位，不沿用旧位置。 |
| `REQUESTING` | 用户主动匹配当前位置或开始导航 | 高精度、12 秒超时、正式节点尚未改变。 |
| `RELIABLE` | 坐标有效且精度满足当前门限 | 可计算到路线的投影与剩余距离。 |
| `LOW_ACCURACY` | 精度超门限、跳点或样本陈旧 | 立即暂停逐向指令，不显示“已到达”。 |
| `OFF_ROUTE` | 连续样本满足偏航滞回 | 暂停旧指令，启动受约束的自动确定性重算；无安全新路线时继续停止。 |
| `WRONG_WAY` | 在走廊内连续三个可靠样本相对最远已达进度反退，且扣除精度后超过 20 米 | 保持当前正式路线但停止旧方向感，显示安全掉头提示；回到最远进度 8 米内后恢复正常指令。 |
| `DENIED/TIMEOUT/ERROR` | 权限、超时或浏览器错误 | 停止监听，保留手动起点和现场求助。 |

一次节点匹配采用保守门限：浏览器精度不高于 50 米，且“最近正式节点距离 + 浏览器精度”不超过 80 米。权限 API 明确为 `granted` 时可在正式快照加载后自动匹配一次；`prompt` 时必须由游客点击，`denied` 或浏览器不支持时显示明确降级。逐向导航采用更严格的 35 米精度、10 秒样本新鲜度、12 m/s 跳点门限、三点偏航/远端分支/反向行走滞回和到达驻留；路线匹配不只取全局最近线段，而是先用前一进度、实际移动和定位不确定性筛选连续候选。页面进入后台会暂停定位与方向指令。

确认偏航或正式路网/运营版本变化后，运行时先停止旧指令，再尝试自动重路由。只有 10 秒内、精度不高于 35 米的定位样本可在设备内保守匹配正式节点；发往路线 API 的意图只包含起终节点、原策略/偏好和期望版本，不包含坐标、精度、时间戳、轨迹、朝向或几何。系统重新获取并完整验证当前快照，线上或经验证离线包均复用同一确定性图算法；替代路线必须具有新指纹，并精确绑定景区、起终点、路网、运营版本、策略与偏好。版本变化还需通过确定性运营重算判定。任何定位、节点、快照、版本或新路线校验失败都会维持 `REROUTE_REQUIRED`，不得恢复旧指令或调用未批准的候选路线提供方。

## 5. 景区路网与路径权重

### 5.1 路网实体

- `route_nodes`：入口、出口、换乘、设施、目的地和普通拓扑节点；几何为 `Point, EPSG:4326`。
- `route_edges`：有向/双向通行边；几何为 `LineString, EPSG:4326`，记录距离、基础耗时、台阶、坡度、路宽、无障碍、道路类型、难度、观光评分和证据；索道/观光车边还记录服务名称、上车、预期等候、乘坐时长和班次依据。
- `route_operational_versions`：一次完整运营状态发布。
- `route_edge_operational_states`：每条边在该版本下的开放状态、拥堵、天气影响、耗时倍率、责任人和有效期。
- `closure_events`：封路或限制事件；变化会使旧指令失效。
- `scenic_published_snapshots`：事务化发布的完整只读包；游客端不拼装半成品表。

道路类型覆盖 `WALKWAY`、`BOARDWALK`、`MOUNTAIN_TRAIL`、`STAIRS`、`CABLEWAY`、`SHUTTLE`。正式 revision 的所有边都必须具有完整路由属性；缺一项即返回 `ROUTING_ATTRIBUTES_UNAVAILABLE`。交通边缺少独立服务元数据时返回 `TRANSPORT_SERVICE_UNAVAILABLE`，不能退化成步行边。

### 5.2 策略公式

所有边权保持非负，以满足 Dijkstra 的正确性：

- 最快：`cost = 基础分钟 × 运营耗时倍率`；
- 最短：`cost = 距离米数`，同距离时以动态预计时间稳定打破平局；
- 观光：`cost = 动态分钟 × (2 - 1.5 × 观光评分/100) × 难度节奏系数`。

天气与拥堵不能由游客端自由填写并直接改变安全结论。它们必须进入短期运营快照，带来源、责任人、采集时间和到期时间；需要关闭的道路应直接发布为 `CLOSED/RESTRICTED`，不能只靠增加权重绕行。

年龄不直接写入路径算法。AI 行程可以根据用户主动提供的年龄段建议“轻松/均衡/活力”与最高难度，但必须由用户确认；核心路由只接收行为约束，避免年龄歧视、隐私扩张和错误安全推断。

### 5.3 索道与观光车语义

- 默认策略只允许四类步行通行边；索道和观光车必须由游客分别勾选，AI 行程沿用同一选择，不得因“更快”静默带上交通工具。
- 一条交通候选路径只允许两个端点，避免把同一次上车等待重复计入每个折线子段。正式预计时间严格等于“上车准备 + 预期等候 + 车内/索道乘坐”，不是按步速换算。
- 导航运行时输出 `BOARD_*`、`RIDE_*`、`ALIGHT_*` 分段提示，剩余 ETA 按当前交通段和后续边计算；线路在地图上使用独立虚线样式。
- `OPEN` 只来自短期运营快照。服务名称与班次依据不证明今天正在运行，票价、末班时间、即时排队和临时停运均不得推测；未知或过期时停止使用该边。
- 无台阶路线只有在交通边被正式标为 `VERIFIED_ACCESSIBLE` 且 `stairs=NONE` 时才可采用，仍需现场核验上下客点、车厢/轿厢和衔接路径。

## 6. 数据库与 SQL 入口

完整 SQL 位于：

- `database/migrations/001_initial.sql`：景区、POI、候选基础实体；
- `database/migrations/003_p0_control_plane.sql`：正式来源、发布、路网、运营状态、路线快照、游览会话、后台审计；
- `database/migrations/004_social_ecosystem.sql`：地点社区、动态、互动、打卡与社交资料；
- `database/migrations/005_scenic_navigation_intelligence.sql`：道路类型/难度/观光权重、动态耗时、导航会话与历史事件；
- `database/migrations/006_formal_offline_navigation_packs.sql`：签名公钥、正式离线包、资产清单、双角色审核和撤回事件；
- `database/migrations/007_travel_group_live_location.sql`：小队邀请、短时位置共享、覆盖式最新点和无坐标生命周期事件；
- `database/migrations/008_formal_scenic_itineraries.sql`：景点游览标签/停留证据和短时确定性个性行程快照；
- `database/migrations/009_formal_place_communities.sql`：地点社区与正式 POI 的租户内一对一绑定；公开状态要求社区核验与有效期齐全，旧候选记录不自动回填；
- `database/migrations/010_navigation_session_lifecycle.sql`：账号级导航会话的路线重放绑定、revision、幂等键、50 米进度档位、封闭原因码与严格无轨迹约束；
- `database/migrations/011_gis_draft_review_workflow.sql`：GIS 候选不可变提交、规范化内容摘要、职责分离审核与追加审计隔离区；
- `database/migrations/012_route_closure_control.sql`：当前正式边上的紧急封闭/限行、独立事后复核、证据化撤回与不可变动作审计；
- `database/migrations/013_route_operational_snapshot_release.sql`：已确认管制事件的全边运营状态编译、不可变候选与独立原子替换；
- `database/migrations/014_gis_formalization_release.sql`：已审核 GIS 的精确拓扑正式化计划、三身份分离发布、正式推荐路线与追加审计；
- `database/migrations/015_scenic_transport_routing.sql`：索道/观光车服务名称、上车/等候/乘坐时间、班次证据和步行边互斥约束；
- `database/rollbacks/`：每个迁移的显式补偿路径。

用户位置不建立“连续轨迹表”。实时定位默认只在设备内存存在；服务端导航历史只保存可由正式路网重现的路线指纹/版本、单调 revision、开始/暂停/重算/完成事件和 50 米档位后的剩余距离。创建与恢复必须重新核验当前正式路线，事件请求不能携带坐标、几何、朝向或 GPS 样本。好友同行位置需要独立的短 TTL、端到端授权和撤销模型，不能复用导航历史长期保存。

## 7. 游客端导航交互

正式运行态页面采用三层：

1. 顶部指令条：下一动作、方向、剩余距离、ETA、当前运营状态；
2. 地图：蓝色定位点、精度圈、正式路线、方向箭头、目的地与附近已审核推荐；
3. 底部控制：开始、暂停/继续、结束、重新定位、求助。

任何 `LOW_ACCURACY`、`OFF_ROUTE`、运营版本变化、离线包过期或网络恢复后的状态不一致都会把顶部指令替换为“已暂停，请核验”，而不是继续播报旧方向。

## 8. AI 个性路线

AI 只负责把自然语言转换成可审计约束，例如：总时长、节奏、兴趣、同行人、休息频率和必须/排除 POI。确定性规划器负责：

1. 从已发布 POI 中匹配候选；
2. 计算停留时间预算；
3. 用时间窗和路网求可行站序；
4. 对每个推荐点给出来源与选择理由；
5. 开放时间、天气、拥堵或安全信息缺少权威数据时拒绝猜测。

“3 小时轻松游玩”不能直接变成一条自由生成的折线；必须生成结构化约束，再由正式路由服务逐段求解。

## 9. 同行与社区导航

同行导航的生产模型分为 `travel_groups`、成员与角色、邀请令牌哈希、短 TTL 位置共享会话、覆盖式最新位置快照和撤销事件。精确位置必须显式同意、随时停止，退出小队后立即不可读；前端只保留当次队友的距离、方向和短时点位。位置消息不得进入公开社区、训练数据或长期导航历史。

地点社区只把“附近内容”绑定到已发布 POI。沿途推荐先要求 POI/设施位于本次 traversal 道路链，再检查前方 120 米走廊与完整游览证据，避免把隔墙、跨谷或不在所选路线上的近邻点误报为沿途。社区 API 还会核验同一景区租户、POI `FIELD_VERIFIED`、正式 publication 与三者有效期，只返回过去 24 小时已审核的公开动态、图片与打卡计数；请求不包含游客坐标。热门照片与评价是 UGC，不得推导实时客流、开放状态或路线安全，并与主导航指令保持视觉和数据隔离。

## 10. 离线地图包

正式离线包必须是带版本、正式快照发布时间、SHA-256、许可、范围、生成时间和有效期的清单，至少包含：自有/获批瓦片、路网快照、运营状态、POI、样式与必要图标。读取接口默认关闭，并要求真数据库、显式开关、完整发布链、活动公钥和职责分离双审核。服务端对规范化完整清单和数据库资产库存做逐项交叉校验；客户端先验 ECDSA，再用增量 SHA-256 流式校验到唯一候选缓存，全部成功后才切换活动登记。

Service Worker 不接收任意 URL 列表，只重新验证活动登记签名并服务清单列出的同景区路径；PMTiles 使用单 Range 读取。API、账号、后台、分享令牌和社区写入始终 network-only。资源中途失败、哈希/长度/类型不一致或存储失败会删除候选缓存，旧活动包不受影响。

地图渲染再执行一层网络隔离：签名 `MAP_STYLE` 只保留 background/fill/line/circle，拒绝 imports、sprite、glyph、raster、外部 URL 和保留 ID；所有 vector source 都改写到同包唯一 `VECTOR_TILES`。`POI_CATALOG` 仅接受有界 WGS84 Point。路网、运营状态、样式、瓦片和 POI 必须匹配同一包号/修订与同一快照版本；地图资产失败时降级为正式路线示意层，包身份变化或过期时停止离线逐向指令。

离线状态下 GPS 仍可工作，`ROUTE_NETWORK` 与 `OPERATIONAL_STATE` 经过再次哈希和完整合同验证后，由在线相同的确定性图算法在设备执行；但运营状态或包过期后必须停止逐向导航。重新联网时先刷新线上运营版本，再决定继续或重算。AI 多站、社区、好友位置和账号历史不属于离线实时能力，断网时明确停用。

## 11. 管理端 GIS 候选审核

`/admin/map-editor` 的本机 v2 草稿可主动提交到租户隔离审核队列。`POST /api/v1/admin/scenic-areas/:id/gis-draft-submissions` 只接受 1–200 个严格 WGS84 候选对象，生成单调 submission revision、稳定内容 SHA-256、不可变对象和追加事件；同一操作者的同一幂等键只能对应同一内容。网络或后台失败不会清除浏览器草稿。

`POST /api/v1/admin/scenic-areas/:id/gis-draft-submissions/:submissionId/review` 只允许不同 OIDC subject 的 `GIS_REVIEWER` 在 workflow revision 1 上提交带 HTTPS 证据的批准或拒绝。运行时还要求真数据库、显式开关、请求方法/路径/时间绑定的可信边缘 HMAC 身份断言、OIDC/MFA 和租户内有效数据库角色。批准结果是 `APPROVED_FOR_FORMALIZATION`，不是正式 publication；第十一号迁移和 N6 审核 API 均禁止候选直写正式路网/POI，后续正式化只能进入第 12.3 节所述的 N9 独立多人发布链。

`GET /api/v1/admin/scenic-areas/:id/gis-draft-submissions` 只分页读取同租户待审 revision 1；`GET /:submissionId` 重建严格候选集合并重算规范化摘要。`/admin/gis-review` 显示不可变版本、候选空间预览、逐对象来源/属性、职责分离状态和审核证据。底图与几何均持续标为候选；审核成功只显示待正式化，不能在此工作台发布。

## 12. 紧急道路管制

`GET/POST /api/v1/admin/scenic-areas/:id/route-operations` 与 `POST /:eventId/review` 构成独立于候选 GIS 的正式运营控制面。读取和写入都要求真数据库、`ROUTE_OPERATIONS_ENABLED=1`、请求路径/方法/60 秒绑定的 HMAC 可信身份断言、OIDC issuer/audience/有效期、MFA 证据和租户数据库角色。

`OPERATIONS_EMERGENCY` 只能选择当前已发布、许可有效、现场核验且当前运营状态为 `OPEN` 的正式边。请求绑定当前 snapshot revision，要求 HTTPS 来源/原因证据、结构化事件类型、10–1000 字现场说明、开始/到期时间、最长七天、幂等键和明确的立即停止确认；重叠事件与陈旧快照被拒绝。事件按开始时间进入现有正式读取查询的失败关闭条件，因此旧导航会停止，但系统不会凭事件自动拼装新的运营快照或猜测绕行。

不同 OIDC subject 的 `RELEASE_ADMIN` 才能在 workflow revision 1 上确认或撤回。确认维持阻断直至到期；撤回只移除本事件作为阻断依据，不证明道路物理开放。每个动作写入不可变 `route_closure_event_actions` 和现有 `admin_audit_events`。`/admin/route-operations` 仅是该受控链路的 UI；没有正式路网、生产身份、官方事件源、值班 SLA 和现场演练时保持不可用。

## 12.1 替代运营快照

`GET/POST /api/v1/admin/scenic-areas/:id/route-operational-releases` 与 `POST /:releaseId/publish` 把 N7 的“立即停止”推进到受控的“新版本安全重算”。它需要独立开关 `ROUTE_OPERATIONAL_RELEASE_ENABLED=1`，并继续要求真数据库、可信边缘身份断言、OIDC/MFA 和租户角色。

`OPERATIONS_EMERGENCY` 的准备请求不含路网、坐标、几何、边状态或任意权重。服务器锁定当前正式快照，拒绝任何未复核有效事件或观测，把所有已确认、未撤回、未到期事件和每条边最新的已复核动态观测保守编译进覆盖全边的新 `RouteOperationalState`，并保存基础/目标版本、精确事件/观测绑定、短有效期和规范化 SHA-256。未来才开始的已确认事件从候选发布时起阻断对应边，避免单一状态快照在事件开始后漏封。

不同 subject 的 `RELEASE_ADMIN` 发布前再次锁定并核对基础快照、事件/观测全集、严格 JSON、版本、有效期和摘要；随后在单一事务内撤下旧 `scenic_published_snapshots`、把旧运营版本标为 `SUPERSEDED`、发布新运营版本和新快照。导航端发现 version 变化后只允许确定性重算；绑定旧 snapshot/version 的离线包失效，必须重新审核和签名。事件、观测或快照到期只会停止导航，不自动证明道路开放或动态因素仍有效。

## 12.2 客流与天气动态观测

`GET/POST /api/v1/admin/scenic-areas/:id/route-operational-observations` 与 `POST /:observationId/review` 只在 `ROUTE_OPERATIONAL_OBSERVATIONS_ENABLED=1`、真数据库、可信身份断言、OIDC/MFA 和租户角色同时成立时开放。`OPERATIONS_EDITOR` 只能选择当前正式快照中的 `OPEN` 边，提交 `LOW/MODERATE/HIGH` 客流、`NONE/RAIN/HEAT/WIND/MULTIPLE` 天气、1–3 倍耗时、观测/失效时间、说明与 HTTPS 一手依据；有效期最长六小时，倍率为 1 只允许 `LOW + NONE`。

不同 subject 的 `OPERATIONS_REVIEWER` 在快照/路网仍一致且观测未到期时确认或拒绝。提交与复核动作、角色、幂等键和证据均写入追加式审计；同一路段同时只允许一项待复核观测。确认只代表可进入完整快照编译，不直接更新游客路线。

第十六号迁移把每条边最新确认观测以 ID 与 SHA-256 精确绑定到不可变发布候选。发布前出现新观测、待复核观测、到期或任何哈希漂移即停止。正式路线 traversal 携带所用倍率、客流和天气，游客页逐段披露并计入 ETA。当前没有六祖镇正式观测数据；传感器/人工采样责任、校准、代表性、异常值、更新 SLA、真库实跑和现场真机仍是生产阻塞。

## 12.3 GIS 正式化与管理发布

`GET/POST /api/v1/admin/scenic-areas/:id/gis-formalizations` 与 `POST /:releaseId/publish` 是候选隔离区到正式数据面的唯一代码通道。它需要 `GIS_FORMALIZATION_RELEASE_ENABLED=1`、真数据库、可信边缘身份断言、OIDC/MFA 和租户角色；缺一项即返回 503。

第二位 `GIS_REVIEWER` 只能读取已经 `APPROVED_FOR_FORMALIZATION` 且内容 SHA-256 仍匹配的不可变提交，并且不能是提交人或原专业审核人。每条 `PATH` 必须显式声明 `PUBLIC/INTERNAL` 和方向；服务器把每段相邻坐标确定性拆成边。入口坐标必须精确同时存在于两层顶点，POI/设施必须精确落在内部顶点，推荐路线的每个顶点也必须属于内部图；不存在距离吸附或猜测连接。来源 URL、许可、坐标精度、静态有效期和短期运营证据必须完整。

不同 `RELEASE_ADMIN` 发布前重新读取对象、重算提交摘要和计划摘要、重建正式 `RouteNetworkManifest` 与 `RouteOperationalState` 并调用现有严格校验器。初始全边 `OPEN` 只能由发布管理员依据运营证据显式确认；旧路网仍有未撤回管制或待发布运营替代候选时拒绝发布。成功事务撤下旧快照/静态版本/运营版本及绑定旧快照的在线离线包，然后写入正式来源、publication、边界、入口、POI、设施、推荐线、节点、边、运营状态和新快照。已下载设备的旧包仍需联网撤回传播和重新签名。
